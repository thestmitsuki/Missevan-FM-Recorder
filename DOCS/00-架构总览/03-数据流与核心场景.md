# 03 · 数据流与核心场景（跨文件 · 跨场景追踪）

> 本文按「场景 → 参与模块 → 关键调用链 → 边界情况」组织，覆盖最核心的端到端流程。
> 文件路径省略前缀：`src-tauri/src/`（后端）/ `src/`（前端）。

## 场景 A：一次完整录制生命周期（核心主线）

### A1 启动装配（lib.rs → detector）

1. `lib.rs::run` 创建 `ConfigManager`（加载 `config.toml` + `anchors/*.toml`，损坏自动备份恢复）。
2. 创建共享单例 `FfmpegRecorder`（进程表全局唯一，**双录防御 #2/#3 的前提**——每次录制 new 一个实例会让进程表形同虚设，历史坑）。
3. `setup` 闭包中启动 `DetectionLoop`（tokio::spawn），持有 `app_state / config_manager / live_cache / mock_store / notifier / recorder_shared / detection_wake / webview_window`。

### A2 检测轮询（detector/loop.rs）

1. 每轮：`sleep(check_interval + random(0..60)s 抖动)`，读取 `config.global.check_interval_secs`（默认 120s）。
2. mock 模式：从 `MockStore` 取数据，**不发真实请求**（跳过网络）。
3. 真实模式：对每个 `enable_check=true` 的主播调用 `MissevanClient::check_live`。
4. 错误分类（`spider.rs`）：`Server`（5XX/429）→ 重试+指数退避，429 额外冷却；`Network` → 重试；`Format` → 不重试；`Other` → 不重试。判定「未知」不算离线。
5. 状态写入 `live_cache`（room_id → is_live）→ `update_anchor` 更新配置 → `build_statuses` 组装 `AnchorStatusUpdate` → `window.emit("recording_status_changed")`。
6. 若 `is_live && enable_check && !is_recording`：进入录制启动流程（A3）。

### A3 录制启动（loop.rs → engine.rs）

1. 磁盘预检 `check_disk_space`（阈值 `disk_space_limit_gb`，0=不限制），不足 → 通知 + 跳过（S2a）。
2. 读取流地址 `get_stream_url`（失败 → 通知 REC_API_FAILED，跳过本轮）。
3. 延迟窗口 `pre_record_delay_secs`：先 `register_pending_start(anchor_id, cancel_token)` 注册进 `AppState.pending_starts`（**可取消**：停止命令据此取消延迟中的启动；无此表时 stop_recording 找不到任务会误报「未在录制中」）；延迟结束复检（仍直播 + 未在录）才真正启动。
4. `start_ffmpeg_recording` 三道防线：
   - **双录防御 #1**：`recorder_shared.is_recording(anchor_id)` 锁内去重（`RC_ALREADY_RECORDING`）；
   - **并发上限**：`max_concurrent_recordings >= 1` 时活跃任务数达上限拒绝（`RC_CONCURRENCY_LIMIT`）；
   - **单实例锁**（进程级，lib.rs 已保证，engine 内不再依赖）。
5. 构建 FFmpeg 命令（`builder.rs`：`-vn` 音频-only / `-f segment` 分段 / `-b:a` 码率 / `-rw_timeout` 读超时 / 用户代理等）→ 渲染输出路径（`template.rs`，空/非法回退默认模板）→ 目标已存在自动 `_2/_3` 去重（非分段）。
6. `spawn` 子进程 → 注册任务进 `AppState.tasks`（anchor_id → Task{cancel_token, handle, output_path, pid}）→ emit 状态 → `monitor_recording` 单独任务监控（A4）。
7. 通知 `REC_START`；录制开始事件同时触发文件缓存刷新。

### A4 录制监控与结束（monitor.rs → cleanup）

1. 每 5s：检查子进程存活 + 磁盘空间（不足 → 通知 DISK，节流 `DiskNotifyThrottle`）。
2. 子进程异常退出：`is_abnormal_exit` 判定（非 cancel 令牌触发）→ `mark_crash_partials` 标记 .part 残留 → `CrashBackoff` 熔断计数（达阈值暂停自动重启，指数退避）→ 通知 `REC_CRASH`。
3. 正常结束/手动停止：`stop_recording` 发 cancel 令牌 → monitor 统一出口：
   - `cleanup_on_recording_end`（录制结束自动清理，按 retention_days / max_total_gb）；
   - 刷新文件缓存 `refresh_recording_files`（emit `recording_files_changed`）；
   - 追加历史 `RecordingSummary`（上限 50 条，托盘「最近录制」数据源）；
   - 发 `REC_END` / `REC_ERROR` 通知；
   - 若 `enable_check` 仍为 true 且配置了自动重试且失败原因可重试 → 按 `max_retries/retry_delay` 安排重试（走 A3 同款防线）。
4. `post_record_action`：录制结束执行（none / open_folder / command——command 有 `${output}` 占位符与超时保护）。

### A5 手动停止（前端 → api/recording_cmds.rs → engine/monitor）

1. 前端「停止录制」→ `stop_recording(anchor_id)`。
2. 先查 `pending_starts`（取消延迟中的启动）；再查 `tasks`（cancel 令牌 + 等待 JoinHandle ≤ 5s）；两者都没有 → `RC_STREAM_UNAVAILABLE`「主播未在录制中」。
3. 兜底：引擎 `processes` 表按 anchor 终止残留 ffmpeg 进程。

### A6 退出（关闭 → do_shutdown）

1. 关闭窗口（close 事件）：`should_hide_to_tray`（`close_behavior == "tray"` 且非「正在退出」）→ 隐藏 + prevent_default；否则正常关闭。
2. `do_shutdown`：保存配置 → 停 DetectionLoop → cancel 所有 tasks（等 JoinHandle ≤5s）→ 从 `try_state` 取回共享 recorder 强制终止残留进程 → `app.exit(0)`。
3. 托盘「退出应用」走同一 `do_shutdown`。

## 场景 B：文件管理链路（扫描 → 页面 → 操作）

```
engine 录制/结束 ──► file_cache 扫描输出目录（fs_walk 安全遍历，不跟随链接）
                        │
                        ├─► FileCacheState（文件表 + 文件夹树 + 扫描日志 ≤20 条）
                        ├─► emit recording_files_changed（增量/全量）
                        ▼
前端 fileStore.startListener ──► FilesView
        │
        ├─ 搜索/日期筛选/类型筛选（前端过滤，纯函数）
        ├─ 重命名 rename_recording_file（录制中文件 is_active 禁改）
        ├─ 删除 delete_recording_file（同禁删 + 防路径逃逸 ensure_within_output_dir）
        └─ 播放 play_recording_file → playerStore（全局单例 audio，队列连播）
```

关键点：
- `path_key()` 统一 `/` 分隔符，避免 Windows `\` 与引擎 `/` 拼接导致的漏判。
- `mark_active`：对照 AppState 活跃输出路径集合标记 `is_active`（前端据此禁删/禁改）。
- `refresh_recording_files` 与 `get_recording_files` 的锁序：先取 active_paths 再锁 cache（防死锁）。
- 播放使用 `convertFileSrc`（asset 协议），`playerStore` 全局 audio 单例跨页面不注销；空 src 不触发 error 事件（修复「切页误报音频加载失败」根因）。

## 场景 C：配置保存与导入导出（config/manager.rs）

1. `save_config`：校验（record_format / output_dir 等字段合法性 + 上限）→ 深拷贝 → `atomic_write_global`（std Mutex 串行化「写 tmp → rename」，失败保留备份 `config.toml.bak.<时间戳>`，保留最近 5 份）→ 若 output_dir 变化 → 重建 FileCache → 若 autostart 变化 → 写系统自启 → emit 状态。
2. `import_config`：文件对话框 → 解析 TOML → 模式（replace 全替换 / merge 保留本地）→ 校验 → 写盘 → 重建缓存 → 返回 `ImportSummary{...}`。
3. `export_config`：TOML 序列化（含 anchors 与全局，敏感字段已混淆 `enc:v1:`）。
4. 前端 `configStore.saveConfig` 与向导 `stagedToConfig.ts` 都收敛到同一命令；**FFmpeg 路径由向导暂存，不写配置**（完成按钮时随 save 落盘）。

## 场景 D：通知链路（notification/dispatcher.rs）

```
触发点（engine/monitor/loop/cmds）
  └─ notifier.notify(code, level, title, message, source?, actionable?)
        ├─ 过滤矩阵（NotifySettings：总开关 enabled + 7 类事件勾选 + system/sound）
        ├─ 系统 toast：windows_toast（AUMID 应用注册，非 PowerShell 兜底）
        ├─ 提示音：notify_sound（默认音）
        ├─ 前端推送：emit "app:notification"（环形缓冲 500 条 + 前端通知中心）
        └─ 记录进 NotificationDispatcher 环形缓冲（get_notifications 供前端）
```

事件码（节选）：`REC_START / REC_END / REC_ERROR / REC_CRASH / REC_API_FAILED / LIVE_START / LIVE_END / DISK_LOW / DISK_WARNING / UPDATE_AVAILABLE / CF_SAVE_FAILED ...`（完整见 `04-附录/01-命令与事件清单.md`）。

## 场景 E：首启向导（wizard 窗口）

1. 首启（无 `config.toml`）：setup 显示 wizard、隐藏 main。
2. 4 步：欢迎 → 基本设置（`wizardStore.staged` 内存暂存）→ 环境检查（`run_wizard_health_check`：FFmpeg/ffprobe 候选、磁盘、写入权限；Windows 可 `download_ffmpeg` 流式下载便携版 + `download:progress` 进度）→ 完成（`finish_wizard`）。
3. `finish_wizard`：销毁向导窗 → 显示/聚焦 main → 刷新文件缓存 → `detection_wake.notify_one()` 立即检测。
4. Linux 分支：不自动下载 FFmpeg，提示 `sudo pacman -S ffmpeg`（Arch）等系统包安装。
5. 向导「完成标记」localStorage 逻辑已移除（只写不读的历史遗留，M7 审查跟进），首启判定仅依赖配置文件存在性。

## 场景 F：调试面板（debug 路由）

- 入口：设置 → 关于 → 调试模式开关（`debugStore`，localStorage `debug_enabled`，默认关）。
- 模块：Overview（环境/工具状态/统计汇总）、Detector（统计快照）、Recorder（活跃任务 + 历史）、FileCache（扫描状态 + 日志）、Logs（实时日志，环形 1000 条 + 级别过滤 + 来源过滤 + 脱敏）、Network（请求记录 500 条）、Mock（模拟数据编辑）、Notifications（通知中心）、Performance（性能采样，空实现）。
- 数据源：`get_debug_info` / `get_detector_stats` / `get_recorder_state` / `get_file_cache_state` / `get_logs` / `get_network_logs` / `get_mock_state` / `export_diagnostic_report`（脱敏导出 PDF/JSON）。
- 诊断导出：`export_diagnostic_report` 走 `infrastructure/checker` + debug 数据组装脱敏报告。

## 场景 G：托盘交互

- 轮询（2s）：`active_count()` + `history` 与上次快照比对，有变化才 `set_menu` 重建（不监听事件，避免竞态）。
- 菜单项：「显示主窗口」「录制中：N」（点击 → emit `tray:open_live_page` → 前端跳转直播页）「最近录制」≤5 条（点击 → 资源管理器选中文件）「退出应用」。
- Linux：不实例化托盘（`try_state` 恒 None → 关闭即退出，见 #12）。

## 场景 H：更新检查

- `check_update`：GET GitHub Releases API → 解析 `tag_name` / 下载链接 → 返回 `{latest, current, download_url}`；404/网络失败返回 Err（前端显示「检查更新失败」，不崩溃）。
- `get_app_info`：关于框静态信息（构建日期 = exe 修改时间）。
- `open_browser`：仅放行 http/https（`is_browsable_url` 防命令注入）。
- 前端在设置页「检查更新」按钮与启动时（`check_updates` 配置）触发。
