# 02 · 整体架构

## 1. 分层总览

项目遵循**经典三层**划分（后端），前端为**单向依赖**的模块化结构：

```
┌────────────────────────────── 前端（Vue 3 + TS） ──────────────────────────────┐
│  views（页面） → stores（Pinia） → services（Tauri 桥接） → types（DTO 契约）   │
│  components（common/layout/ui）  lib（纯函数）  locales（i18n）  router         │
└───────────────┬────────────────────────────────────────────────────────────────┘
                │ invoke(命令) / listen(事件)
┌───────────────▼────────────────────────────────────────────────────────────────┐
│  api 层（Tauri 命令，9 模块 54 命令）—— 薄壳：参数校验 → 调用 domain → 包装错误 │
├────────────────────────────────────────────────────────────────────────────────┤
│  domain 层（业务规则，纯 Rust，可单测）                                        │
│   ├─ config   配置模型 + 原子读写/备份/导入导出                                 │
│   ├─ detector 检测循环 + 统计 + 直播状态归并                                   │
│   ├─ recorder 录制引擎 + 进程监控 + 命令构建 + 模板渲染 + 磁盘保护              │
│   ├─ services 文件缓存 / 清理 / 安全遍历                                       │
│   ├─ spider   猫耳 API 客户端（检测/资料/网络插桩）                            │
│   └─ tools    FFmpeg/ffprobe 路径解析 + 子进程辅助                              │
├────────────────────────────────────────────────────────────────────────────────┤
│  infrastructure 层（平台/框架适配）                                            │
│   ├─ state       AppState（任务表/统计/头像缓存）+ MockStore                   │
│   ├─ logging     文件日志 + 环形缓冲 + 网络插桩（tracing）                     │
│   ├─ notification 通知调度（事件→系统 toast/声音/前端推送）                    │
│   ├─ tray        系统托盘动态菜单                                               │
│   ├─ checker     健康检查（FFmpeg/磁盘/权限）                                  │
│   ├─ crypto      敏感字段轻量混淆（enc:v1:）                                   │
│   ├─ error       统一错误模型（码/类别/严重级）                                │
│   └─ single_instance 单实例文件锁                                              │
└────────────────────────────────────────────────────────────────────────────────┘
```

**依赖方向纪律**（代码中严格可见）：
- `api → domain + infrastructure`；`domain` 内部模块互不依赖（除 `recorder → services/file_cache` 与 `spider` 这类协作调用）；
- `domain` **不反向依赖** infrastructure 的 error/notification（除少数显式协作，如 recorder 用 notification 发通知——这是审查看点，见 §6）；
- 前端 `views → stores → services`，组件只消费 store，页面内不直接 `listen` 事件（统一走 `services/events.ts` → store）。

## 2. 双窗口架构

`tauri.conf.json` 定义两个窗口，**加载同一套前端**，靠窗口 label 分流：

| 窗口 | label | 角色 | 前端分流依据 |
| --- | --- | --- | --- |
| 设置向导 | `wizard` | 首启 4 步引导（欢迎→基本设置→环境检查→完成） | `isWizardWindow()`（`services/window.ts`） |
| 主窗口 | `main` | 全部业务页面（直播/文件/设置/调试） | 默认（非 wizard） |

关键行为：
- 首启：`setup` 中显示 wizard、隐藏 main；非首启：`wizard.destroy()`（避免触发前端 `onCloseRequested` preventDefault 竞态）。
- `App.vue` 按 `isWizardWindow()` 决定渲染 `WizardView` 还是 `AppLayout + router-view`。
- 向导「完成」：`finish_wizard` 关闭向导窗 → 显示聚焦主窗 → 刷新文件缓存 → 唤醒检测循环（`detection_wake.notify_one()`）。
- 路由守卫：`/wizard` 只允许 wizard 窗；`/debug` 仅在 `debugStore.enabled` 时可达。

## 3. 前后端通信契约

### 3.1 命令（invoke）—— 54 个，按权限分组（详见 `04-附录/01-命令与事件清单.md`）

| 分组 | 权限文件 | 命令数 | 模块 |
| --- | --- | --- | --- |
| 主播 | `anchors.toml` | 8 | `api/anchor_cmds.rs` |
| 配置 | `config.toml` | 8 | `api/config_cmds.rs` |
| 文件 | `file.toml` | 6 | `api/file_cmds.rs`（含 `pick_output_dir`） |
| 录制 | `recording.toml` | 2（start 为占位禁用） | `api/recording_cmds.rs` |
| 调试 | `debug.toml` | 14 | `api/debug_cmds.rs` |
| Mock | `mock.toml` | 8 | `api/mock_cmds.rs` |
| 更新 | `update.toml` | 3 | `api/update_cmds.rs` |
| 向导 | `wizard.toml` | 4 | `api/wizard_cmds.rs`（含 `run_wizard_health_check`） |
| 文件系统 | `fs_utils.toml` | 1 | `api/fs_utils.rs` |

> 注：`lib.rs` setup 闭包中调用的 `config_cmds::allow_output_dir` 是**内部辅助函数**（FS scope 放行），不是 Tauri 命令，不计入 54。

**能力边界**：`capabilities/default.json` 授权 `main` 窗全部业务命令；`capabilities/wizard.json` 仅授权向导命令 + 配置读取（`get_config` / `run_wizard_health_check` 等），实现「向导窗拿不到调试/文件/主播管理权限」。

### 3.2 事件（emit/listen）—— 7 个

| 事件 | 方向 | 载荷 | 生产者 |
| --- | --- | --- | --- |
| `recording_status_changed` | 后端→前端 | `AnchorStatusUpdate` | engine / monitor / detector |
| `recording_files_changed` | 后端→前端 | `RecordingFilesPayload` | file_cache 扫描 |
| `app:notification` | 后端→前端 | `Notification` | NotificationDispatcher |
| `debug:log` | 后端→前端 | `LogEntry`（节流 100 条/s） | LogLayer |
| `mock:status_changed` | 后端→前端 | `MockStatusChanged` | mock_cmds |
| `tray:open_live_page` | 托盘→前端 | 无 | TrayManager |
| `download:progress` | 后端→前端 | `{ percent, stage }` | wizard_cmds（Windows FFmpeg 下载） |

前端统一在 `services/events.ts` 注册监听（fan-out 到 handler Set），store 通过 `onXxx` 订阅，页面组件不直接 listen。

## 4. 应用启动流程（`lib.rs::run`）

```
main.rs → missevan_recorder_lib::run()
 ├─ install_panic_hook()（tracing::error + 默认 hook 链式）
 ├─ init_logging()（tracing 文件 + LogBuffer + 脱敏）
 ├─ 单实例锁 acquire()（失败 → 提示并退出）
 ├─ ConfigManager::new()（加载/损坏恢复/备份）
 ├─ 各共享状态：RecorderState / FfmpegRecorder(共享单例) / FileCache /
 │   AvatarCache + NegativeCache / MockStore / LogBuffer / NetworkStore /
 │   live_cache / detection_wake / notifier / config_manager
 ├─ Tauri Builder：
 │   ├─ plugins：dialog / notification / autostart("MissevanRecorder", --minimized) / opener
 │   ├─ .manage() 注入全部状态
 │   ├─ .invoke_handler(54 命令)
 │   ├─ setup 闭包：首启判定 → wizard 窗显示或销毁 → 启动 DetectionLoop
 │   │   → 注册 on_window_event（close→tray/exit 决策）→ app_handle 注入
 │   └─ on_window_event（close）：should_hide_to_tray 决策
 └─ run()
```

## 5. 核心运行时对象（共享状态）

| 对象 | 类型 | 用途 | 消费方 |
| --- | --- | --- | --- |
| `RecorderState` | `infrastructure::state::app_state` | 任务表 `tasks`、pending_starts、历史、崩溃计数、头像缓存、mock_store | api 全部命令 |
| `FfmpegRecorder`（共享单例） | `domain::recorder::engine` | 进程表 `processes`（双录防御 #2/#3 前提） | loop / monitor / shutdown |
| `ConfigManager` | `domain::config::manager` | 全局配置 + anchors 持久化 | 所有命令 |
| `NotificationDispatcher` | `infrastructure::notification::dispatcher` | 通知过滤 + 分发（系统/声音/前端/环形缓冲） | engine / monitor / loop / cmds |
| `FileCacheHandle` | `domain::services::file_cache` | 文件扫描缓存 + 事件推送 | file_cmds / cleanup / engine |
| `DetectionLoop` | `domain::detector::loop` | 后台检测循环（可停止/唤醒） | 启动装配 / finish_wizard / debug |
| `MockStore` | `infrastructure::state::mock_store` | mock 主播表 + 模式开关 | DetectionLoop / mock_cmds |
| `live_cache` | `Mutex<HashMap<room_id,bool>>` | 主播直播状态缓存 | loop / anchor_cmds |
| `detection_wake` | `tokio::sync::Notify` | 立即唤醒一次检测 | finish_wizard |
| `LogBuffer` / `NetworkStore` | logging | 调试页数据源 | debug_cmds / spider 插桩 |

## 6. 架构审查看点（重要观察）

1. **domain 反向依赖 infrastructure 的例外**：`recorder/engine.rs`、`monitor.rs`、`spider.rs` 使用 `NotificationDispatcher` / `logging::network` / `state::app_state`——严格分层角度这是「domain 触达 infrastructure」。**设计动机**：通知与插桩是横切关注点，作者以注释记录了取舍（如网络插桩不用 reqwest middleware，改在调用点记录 + 进程级单例 store）。后续新增领域逻辑时请沿用该惯例并在注释中说明，不要悄悄引入新的反向依赖面。
2. **状态归并点统一在后端**：直播状态 = `merge_live_state(api_live, is_recording)`，在 engine / monitor / detector 三个推送来源处统一生产，前端不重复归并（避免事件时序回闪）。
3. **锁序纪律**：文件缓存命令先取 active_paths 再锁 cache（避免与 refresh 侧锁序反转死锁）；`ConfigManager` 原子写用 std Mutex（写段无 await）。
4. **命令注册可见性坑**：`#[tauri::command]` 生成 `__cmd__xxx` 宏，命令须 `pub(crate)` 才能被 `lib.rs` 的 `generate_handler!` 全路径引用（`wizard_cmds.rs` 头部注释记录的 E0255/E0603 坑）。
5. **Tauri 版本注意**：Cargo.toml 中 `tauri = "2"` 语义版本无精确锁定，`Cargo.lock` 实际锁定；升级依赖后必须跑 `cargo test`（大量单测依赖具体行为，如通知过滤矩阵、模板渲染、路径清理）。
